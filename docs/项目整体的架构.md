# 智能法律文书生成 Agent 平台 - 技术设计文档

## 1. 系统概述

本系统旨在通过 Agent 架构结合 RAG 技术，打造一个多模态输入的法律文书自动生成引擎。系统能够解析用户提供的多元证据材料（文本、图像、音视频），将其结构化为案件事实（Event），并基于本地化的法律法规知识库进行精准检索，最终自动生成符合法定格式要求（如起诉书、答辩状）的法律文书预印本。

## 2. 技术栈选型建议

在你的需求基础上，我为你补全了具体的实现组件建议：

* **核心 LLM / VLM：** Qwen-Max / Qwen-Plus（负责复杂逻辑推理与 Tool Calling）；Qwen-VL（负责图像、视频帧的多模态理解与图文 OCR 解析）。
* **多模态解析：** Whisper / SenseVoice（用于录音、视频音频的 ASR 语音转文本及时间戳提取）。
* **RAG 检索框架：** BGE-m3（多语言向量化嵌入，支持长文本）、BGE-Reranker-v2（重排序模型，提升检索精度）。
* **基础开发框架：** Python + PyTorch + LangChain / AutoGen（用于构建 Agent的 ReAct 逻辑与工作流）。
* **向量数据库：** Milvus 或 Qdrant（支持稠密向量检索与 Metadata 标量混合过滤）。

## 3. 核心模块详细设计

### 3.1 多模态证据解析模块 (Multimodal Parsing)

法律案件中的证据清单通常是碎片化的。本模块的核心是将非结构化数据转化为带有时间线索的文本。

* **文本 (Text)：** 直接清洗，提取关键信息。
* **图像 (Image)：** 调用视觉语言模型（如 Qwen-VL）。不仅要进行 OCR 提取图片中的文字（如合同条款、微信聊天记录），还要输出**场景描述解释**。
* **录音 (Audio)：** 使用 ASR 模型转写。**技术细节：** 必须开启字级别/句级别的时间戳（Word-level Timestamps），输出格式规整为 `[HH:MM:SS] 说话人A: 内容`，并提取核心争议时间点。
* **视频 (Video)：** 采用抽帧策略（如每秒 1 帧）交由 VLM 提取画面描述，同时提取音频轨交由 ASR 处理，最后通过时间戳进行**音画对齐融合**。

### 3.2 案件事实结构化模块 (Structured Event Extraction)

为了减少大模型在后续 RAG 检索中的幻觉，需要将解析后的多模态文本转化为强类型的数据结构。建议使用 Pydantic 定义 `Class Event`，利用 LLM 的 Function Calling 强制输出 JSON：

```python
class LegalEvent(BaseModel):
    evident_type: Literal["文本", "图片", "视频", "录音"]
    time: Optional[datetime] = Field(description="事件发生的具体时间，精确到可用范围")
    place: Optional[str] = Field(description="事件发生地，涉及管辖权判定")
    cause: str = Field(description="事件起因/基础法律关系，如：民间借贷、交通事故")
    process: str = Field(description="事件经过详述")
    result: str = Field(description="当前状态或造成的损害后果")

```

*法学视角提示：* 这里的 `place` 对法律文书至关重要，它直接决定了**管辖法院**的选择（原告就被告原则或侵权行为地原则）；`time` 决定了**诉讼时效**以及**新旧法适用**的问题。

### 3.3 法律知识库与 RAG 模块 (Legal RAG Pipeline)

法律文本的 RAG 与通用 RAG 不同，绝对不能简单的按字数（如 500 tokens）暴力切分（Chunking），否则会导致法条前后文语境割裂。

**1. 知识库构建与清洗：**

* **语义切分：** 严格按照 Markdown 的层级，以“**编-章-节-条-款-项-目**”为最小 Chunk 单元进行切分。
* **Metadata 注入（至关重要）：** 在向量数据库中，除了存储法条文本的 Embedding，必须为每个 Chunk 建立标量字段：
* `law_name`: 所属法规名称（如《中华人民共和国民法典》）
* `article_num`: 第几条
* `applicability_scope`: 适用范围（民事/刑事/行政）
* `applicability_object`: 适用对象
* `effective_date`: 生效时间
* `repeal_date`: 失效时间（用于过滤已废止法条）



**2. 混合检索与重排 (Hybrid Search & Reranking)：**

* 基于 `LegalEvent` 中的内容生成 Query。
* **初筛：** 利用 BGE 模型进行向量相似度检索（Top-20），**同时强制结合 Metadata 过滤**（例如：事件 `time` 必须在法条的有效时间 `effective_date` 之后）。
* **精排：** 将 Top-20 结果送入 BGE-ranker 模型，结合用户问题进行交叉注意力计算，输出最相关的 Top-5 法条作为最终的法律依据。

### 3.4 Agent 推理与文书生成模块 (Agent Generation)

使用 ReAct (Reasoning + Acting) 范式来驱动模型。

1. **Thought (思考)：** 模型分析当前的 `LegalEvent` 以及用户的文书需求（如：起诉书）。判断需要哪些构成要件（原告被告信息、诉讼请求、事实与理由）。
2. **Action (行动)：** 调用工具。
* `Tool 1`: RAG 检索工具（输入案件经过，获取适用法条）。
* `Tool 2`: 长期记忆提取（获取该类型案件的固定行文模板和常见法规，如借贷纠纷必引用的民法典合同编条款）。


3. **Observation (观察)：** 获取检索到的法条和模板。
4. **Generate (生成)：** 根据法定文书规范输出预印本。

## 4. 评价体系 (Evaluation Framework)

为了确保系统的可用性和专业性，采用人工与机器双轨评价机制。

### 4.1 专家盲评 (一线律师评价)

邀请 5 名执业律师，对模型生成的预印本进行双盲测试（不告知是模型生成的），评分标准如下（总分 25 分）：

| 评价维度 | 评分标准 (0-5分) | 法学考量点 |
| --- | --- | --- |
| **格式正确性** | 0=完全混乱; 5=无需修改直接可用 | 首部、正文、尾部结构是否符合最高法文书规范。 |
| **内容完整性** | 0=缺失关键要素; 5=要素齐备 | 诉讼请求是否明确？事实依据和法律依据是否挂钩？ |
| **逻辑条理性** | 0=前后矛盾; 5=逻辑闭环且严密 | 论述是否遵循“三段论”（大前提法条，小前提事实，结论诉求）。 |
| **内容准确性** | 0=存在幻觉/虚构事实; 5=精准还原 | 证据材料转化为事实过程中的客观性，无主观臆断。 |
| **法条适用性** | 0=引用错误/废止法条; 5=法条精准且恰当 | RAG 检索的法条是否切中案件要害，是否存在适用冲突。 |

### 4.2 LLM 机评 (Gemini 3.1 自动化评估)

将 Gemini 3.1 部署为 `Judge Agent`。

* **输入：** 原始多模态文本、标准答案（人类律师撰写的金标准文书）、Qwen 生成的预印本文书。
* **评估 Prompt 策略：** 让 Gemini-3.1 扮演资深法官或合伙人律师，重点进行 **“一致性检验 (Consistency Check)”**（对比生成事实与原始证据是否有偏差）和 **“法律逻辑连贯性检验”**。

## 5. 项目后续优化建议

1. **增加“反事实检验”机制：** 在 Agent 内部引入一个“反方辩友” Agent。例如系统生成了起诉书，反方 Agent 尝试从答辩状的角度攻击起诉书的漏洞，通过一轮自我博弈（Self-Refine）来提升最终文书的质量。
2. **文书可解释性 UI：** 虽然初期不需要前端界面，但未来落地时，生成的文书中引用的事实和法条，必须能高亮并溯源到用户上传的“第 X 秒的录音”或“图 Y”，这对于律师微调来说是刚需。

这份设计文档为你搭建了从底层数据处理到顶层逻辑生成的完整闭环。你在工程实现时，可以重点优先攻克 **RAG 法规数据的 Metadata 标注切分** 和 **Pydantic 强制结构化输出** 这两道关卡。
