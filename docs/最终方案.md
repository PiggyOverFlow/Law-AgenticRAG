# LawRAG 最终方案技术文档

本文档基于当前项目实际代码实现编写，重点说明项目中 **RAG（检索增强生成）** 与 **Agent（智能体）** 的调用链路、核心设计思路以及已实现功能清单。文档面向开发团队，尽量以“当前真实实现”为准，不对尚未完成或仅在配置中声明但未进入主链路的能力做过度承诺。

涉及的核心入口文件：

- `main.py`
- `src/rag/retriever.py`
- `src/agent/legal_agent.py`
- `src/rag/chunker.py`
- `src/rag/vector_db.py`
- `src/data/dataset_loader.py`
- `src/generation/document_generator.py`
- `src/parsers/multimodal_parser.py`

## 1. 详细调用链路

当前项目实际存在两条主路径：

1. **法律问答路径**：`main.py ask`，以 RAG 为主，输出“回答 + 法条引用 + 检索轨迹”。
2. **文书生成路径**：`main.py generate`，以 Agent 为主，调用 RAG 检索法条，再生成正式文书。
两条路径共享同一套法律知识库，但是否启用 Agent 不同。

### 1.1 法律问答路径：用户问题 -> 检索 -> 回答

适用命令：

```bash
python main.py ask --query "用户法律问题"
```

#### 1.1.1 调用流程概览

```text
用户输入问题
  -> main.py / LawRAG.answer_query()
  -> LegalRAG.answer_with_citations()
  -> LegalRAG.search_with_trace()
  -> QueryAgent 规划检索
  -> EmbeddingModel 生成 query 向量
  -> VectorDBManager.search() 在 Milvus-lite 检索
  -> Reranker 做规则重排
  -> 多轮聚合、去重、截断
  -> LegalRAG._build_issue_outline()
  -> LegalRAG._build_contrastive_cot_from_results()
  -> LegalRAG._synthesize_answer()
  -> 返回 answer / citations / trace / issue_outline / contrastive_cot
```

#### 1.1.2 分步骤说明

**步骤 1：CLI 入口接收问题**

- `main.py` 中 `ask` 子命令负责接收 `--query` 与可选的 `--case-date`。
- 入口调用 `LawRAG.answer_query()`。
- `LawRAG.answer_query()` 仅做一层封装，进一步调用 `self.rag.answer_with_citations()`。

**步骤 2：进入 RAG 主控方法**

- `LegalRAG.answer_with_citations()` 是问答路径的顶层方法。
- 它首先调用 `LegalRAG.search_with_trace()` 做检索。
- 如果没有命中法条，直接返回“未检索到相关法条”的降级结果。

**步骤 3：QueryAgent 做检索前规划**

`search_with_trace()` 内部首先调用 `QueryAgent` 完成查询规划。这里的 `QueryAgent` 是 RAG 内部的“检索规划器”，不是文书生成用的 `LegalAgent`。

QueryAgent 当前会做：

1. `should_rewrite()`：判断 query 是否过短、是否存在模糊指代，决定是否改写。
2. `rewrite_query()`：必要时将 query 改写为更完整、可检索的表达。
3. `extract_keywords()`：抽取高信息密度关键词。
4. `build_contrastive_example()`：构造对比问题、重点词、陷阱词，用于后续重排。
5. `extract_legal_elements()`：抽取主体、主体关系、请求项。
6. `plan_issue_queries()`：生成主争点、子争点及多条检索 query。

这些步骤优先使用 `LLMBackend` 进行 JSON 输出；若 LLM 不可用，则回退到规则方法。

**步骤 4：触发 RAG 检索**

`search_with_trace()` 会根据配置执行多轮 Agentic-RAG 检索：

- 默认读取 `top_k_initial / top_k_final / agentic_max_rounds / agentic_min_rounds`。
- 每一轮：
  1. 使用当前 query 提取关键词。
  2. 若启用 contrastive，则使用增强后的 retrieval query。
  3. 调用 `_dense_search()`。
  4. 调用 `Reranker.rerank()` 做规则重排。
  5. 将每轮候选跨轮聚合、去重。

当前主检索链路是：

- **Dense Retrieval**：`EmbeddingModel.encode_single(query)` 生成向量
- **Vector Search**：`VectorDBManager.search()`
- **Rule Rerank**：`Reranker.rerank()`

说明：

- 当前主路径没有把 `keyword_search()` 纳入融合召回。
- `keyword_search()` 已实现，但仍属于可扩展能力，不是主流程的一部分。

**步骤 5：向量库查询**

`VectorDBManager.search()` 在 Milvus-lite 上执行向量检索：

- 存储字段包括：`id / embedding / law_name / article_num / content / level / metadata / effective_date / repeal_date`
- 支持 `case_date` 过滤：
  - `effective_date <= case_date`
  - `repeal_date == '' or repeal_date >= case_date`

因此当前系统已支持“按案件时间检索历史有效版本”。

**步骤 6：重排**

`Reranker.rerank()` 不使用单独 Cross-Encoder 模型，而是当前代码内置的规则重排器。其综合考虑：

1. 原始向量距离
2. 关键词命中
3. 自适应 IDF 加权
4. 路径命中
5. 路径重点命中
6. 法律优先级加权
7. contrastive focus / trap 调整

最终使用 `rerank_score` 排序，而不是原始 `distance`。

**步骤 7：检索结果注入回答阶段**

`answer_with_citations()` 会把每条命中法条整理为两部分：

- `citations`
  - 法律名称
  - 条号
  - 原始距离
  - 最终排序分
  - 生效/失效时间
  - 体系定位
- `evidence_items`
  - 供后续回答生成使用的上下文块

同时，系统会基于：

- contrastive example
- 命中法条中的 focus/trap 信号
- issue outline

构造一份 `contrastive_cot`，作为后续回答生成阶段的显式对比推理骨架。

**步骤 8：构建回答提纲**

`LegalRAG._build_issue_outline()` 会根据问题内容和命中证据自动选择回答模式：

1. `civil_issue_analysis`
   - 民商事争点分析
2. `legal_basis_lookup`
   - 单纯法条依据检索
3. `criminal_procedure_basis`
   - 刑事程序/侦查措施类问题

这是为了避免所有问题都被套入民商事“请求权分析模板”。

**步骤 9：调用 LLM 生成回答**

`LegalRAG._synthesize_answer()` 使用 `LLMBackend.generate()` 发起最终回答生成。

生成阶段会把以下信息注入 prompt：

- 用户原始问题
- issue outline
- contrastive_cot
- 每条法条证据块
- 路径信息、定位信息、优先级提示

这里的 `contrastive_cot` 不是自由发散的长链路思维，而是当前代码中显式构造的“对比驱动推理骨架”，包含：

- 对比问题
- 关键差异 `delta`
- 应重点论证的 `focus_terms`
- 应避免误用的 `trap_terms`
- 支持证据卡片
- 争点定位 / 支持依据 / 混淆排除 / 结论边界 四步推理框架

问答输出会要求模型额外生成“对比辨析”小节，用于说明哪些规范应适用、哪些规范虽然相似但不应误用。

如果 LLM 不可用，则回退到 `_fallback_answer()`，输出结构化降级回答。

**步骤 10：返回给用户**

最终 `main.py ask` 输出：

- `issue_outline`
- `answer`
- `citations`
- `trace`

当前 `answer_with_citations()` 还会一并返回：

- `contrastive_example`
- `contrastive_cot`

其中 `trace` 是多轮检索轨迹，记录每轮使用的 query、关键词、命中数量等信息。

### 1.2 文书生成路径：证据 -> Agent -> 检索 -> 生成文书

适用命令：

```bash
python main.py generate --evidence "..." --type "起诉书"
```

#### 1.2.1 调用流程概览

```text
用户输入证据文件 + 文书类型
  -> main.py / LawRAG.parse_evidence()
  -> MultimodalParser.parse_case_facts()
  -> DocumentGenerator.generate_document()
  -> LegalAgent.run()
  -> StateGraph:
       fact_extraction
       -> rag_search
       -> evidence_filter
       -> template_retrieval
       -> generate
  -> LLMBackend.generate()
  -> 输出正式文书正文
```

#### 1.2.2 分步骤说明

**步骤 1：证据解析**

- `main.py generate` 接收证据文件列表。
- `LawRAG.parse_evidence()` 调用 `MultimodalParser.parse_case_facts()`。
- 当前 parser 的实际完成情况：
  - 文本证据路径较完整
  - 图片 OCR / 音频 ASR / 视频抽帧为占位实现或弱实现

因此，当前 Agent 文书生成最稳定的输入仍然是文本证据。

**步骤 2：CaseFacts 构造**

`parse_case_facts()` 会生成：

- `events`
- `evidence_summary`
- `key_disputes`

这些内容后续会被注入 Agent。

**步骤 3：DocumentGenerator 组装上下文**

- `DocumentGenerator.generate_document()` 构造 `context`：
  - `task`
  - `case_facts`
  - `document_type`
  - `user_request`
- 然后调用 `LegalAgent.run(context)`。

**步骤 4：进入 Agent 状态图**

`LegalAgent.run()` 使用本地实现的 `StateGraph` 执行节点流转。

当前节点如下：

1. `fact_extraction`
2. `rag_search`
3. `evidence_filter`
4. `template_retrieval`
5. `generate`

这不是纯 LLM 自由决策的工具调用，而是：

- **状态图驱动**
- **条件路由驱动**
- **节点内调用工具**

**步骤 5：Agent 节点执行细节**

`fact_extraction`

- 调用 `FactExtractionTool`
- 从 `CaseFacts` 中提取：
  - 事件数量
  - 证据摘要
  - 关键争议点
  - 时间线
- 同时更新 `step / query_strategy / retry_reason`

`rag_search`

- 调用 `RAGSearchTool`
- 内部不是单条 query，而是基于：
  - `user_request`
  - `evidence_summary`
  - `key_disputes`
  - `QueryAgent.extract_legal_elements()`
  - `QueryAgent.plan_issue_queries()`
  组合生成多条检索 query

检索策略分为：

- `focused`
- `balanced`
- `broad`

Agent 会根据重试轮次升级策略：

- 第 1 轮：`focused`
- 第 2 轮：`balanced`
- 第 3 轮及以后：`broad`

`evidence_filter`

- 对候选法条再做证据级筛选
- 使用案件中的主体、争议焦点、时间线、对比检索信号做二次打分
- 目标是抑制错引、减少上下文膨胀

`template_retrieval`

- 调用 `TemplateRetrievalTool`
- 从 `templates/` 目录读取文书模板
- 若找不到模板，则返回内置默认模板

`generate`

- 汇总：
  - 证据摘要
  - 争议焦点
  - 主体结构
  - 主体关系
  - 请求项
  - 争点规划
  - 对比检索提示
  - contrastive CoT 审查骨架
  - 法条上下文簇
  - 模板文本
- 调用 `_generate_document()`，最终使用 `LLMBackend.generate()` 输出文书

#### 1.2.3 Agent 如何选择并执行工具

当前 Agent 的工具调用不是 OpenAI Function Calling 风格，也不是自由文本 ReAct 解析，而是**显式封装为 Tool 类并由状态图节点直接调用**。

已实现工具包括：

1. `rag_search`
   - 作用：检索法条
   - 执行方：`RAGSearchTool`
2. `template_retrieval`
   - 作用：读取模板
   - 执行方：`TemplateRetrievalTool`
3. `fact_extraction`
   - 作用：从 `CaseFacts` 提炼关键事实
   - 执行方：`FactExtractionTool`

当前未实现的 Agent 工具能力：

- 并行工具调用
- 代码执行
- 外部搜索引擎调用
- 数据库直接 SQL 查询

说明：

- 向量数据库查询实际由 `rag_search` 工具内部触发
- Agent 自身不直接操纵 Milvus

## 2. 核心设计思路

### 2.1 RAG 设计

### 2.1.1 文档切分策略

当前采用 **“按条为主、树状结构增强上下文”** 的切分策略。

核心实现：

- `LawChunker.chunk_law_text()`
- `LawChunker._finalize_chunk()`

设计要点：

1. 识别法律层级：`法 -> 编 -> 章 -> 节 -> 条 -> 款 -> 项 -> 目`
2. 以“条”为基本 chunk 单元
3. 同时构建 `LawStructureTree`
4. 为每个 chunk 附加结构化上下文：
   - `structure_path`
   - `structure_hierarchy_path`
   - `structure_locator`
   - `context_text`
   - `structure_children`

这样做的原因：

- 法律条文强依赖体系位置
- 单条正文脱离“编/章/节”容易丢失解释语境
- 便于后续做路径重排和小簇上下文注入

### 2.1.2 retrieval_text 设计

每个 chunk 单独生成 `retrieval_text`，格式固定为：

```text
法律名称：...
体系路径：...
条号：...
正文：...
```

当前向量化时优先使用 `retrieval_text`，而不是直接使用 `content`。

设计原因：

- 避免 embedding 只记住条文本身，而丢掉所属体系
- 让“法名 + 路径 + 条号 + 正文”一起参与召回

### 2.1.3 Embedding 模型选择

当前 Embedding 层由 `EmbeddingModel` 实现，支持两种模式：

1. **Ollama 模式**
   - 默认配置使用 `bge-m3`
2. **本地 Hugging Face 模式**
   - 支持从本地路径加载 embedding 模型

当前配置默认仍偏向：

- 向量模型：`bge-m3`
- 向量维度：1024

选型理由：

- `bge-m3` 适合中英混合与长文本语义检索
- 1024 维在法律条文检索场景中表现较稳
- Ollama 接入简单，便于本地部署

### 2.1.4 向量数据库选型

当前使用：

- **Milvus-lite**

核心原因：

1. 本地文件模式部署简单
2. 不依赖独立服务集群
3. 支持向量检索 + 元数据过滤
4. 适合当前单机研究型项目阶段

当前库内 schema 包括：

- `id`
- `embedding`
- `law_name`
- `article_num`
- `content`
- `level`
- `metadata`
- `effective_date`
- `repeal_date`

### 2.1.5 检索策略

当前检索策略是：

**Dense Retrieval +agentic-Ranker (谁急奖励函数) + Multi-round Agentic Query Planning**

细分如下：

**第一层：QueryAgent 规划**

- 判断是否改写
- 提取法律要素
- 抽取关键词
- 规划争点 query
- 构造 contrastive example

**第二层：Dense Search**

- 使用 embedding 向量检索 Top-K 初始候选

**第三层：Rule Rerank**

重排综合考虑：

1. 原始距离
2. 关键词命中
3. IDF 区分度
4. 路径命中
5. 路径重点命中
6. 法律优先级加权
7. contrastive focus / trap 信号

**第四层：跨轮聚合**

- 多轮 query 改写
- 跨轮去重
- 取最优 `rerank_score`

**第五层：Contrastive CoT 骨架生成**

- 基于 contrastive example、命中法条、focus/trap 命中和 issue outline
- 构造结构化的对比推理骨架，而不是只把 contrastive 信息当作普通提示词
- 在问答端用于生成“对比辨析”，在文书端用于生成前内部审查

### 2.1.6 历史版本与增量索引

当前 RAG 已实现两项比较关键的知识库工程能力：

**1. 增量索引**

- 数据加载时计算 `source_hash`
- 每部法律构造：
  - `source_law_id`
  - `version_id`
  - `source_hash`
- `LawIndexBuilder.build_incremental_index()` 只处理新增或变更法律
- `LegalRAG.build_index()` 在写入前按 `source_law_id` 删除旧版本 chunk

**2. 按案件时间检索历史有效版本**

- `VectorDBManager._build_expr()` 支持 `case_date`
- 检索时按 `effective_date / repeal_date` 做过滤
- 同时在 Python 层再做一次兜底判断

这使得系统不需要每次全量重建 embedding，也支持“按案件发生时间”检索历史有效法条。

### 2.1.7 技术权衡

当前 RAG 方案的权衡如下：

优点：

- 层级上下文信息保留较好
- 检索过程可解释
- 支持增量更新与历史版本过滤
- 多轮 query 规划优于单轮向量检索

代价：

- 主检索仍然主要依赖 dense search
- 稀疏检索尚未进入主融合链路
- 重排是规则型，不是训练型 reranker
- 规则越来越多后需要持续维护

### 2.2 Agent 设计

### 2.2.1 Agent 类型与运行时

当前 Agent 不是“完全开放式自主智能体”，而是：

- **LangGraph 风格的状态图 Agent**
- 运行时使用本地实现的轻量级 `StateGraph`
- 节点由代码显式定义
- 路由由条件函数决定

这意味着当前 Agent 更偏工程化、可控式，而非强自主型多工具智能体。

### 2.2.2 Agent 状态

`AgentState` 当前维护的关键信息包括：

- `step`
- `thoughts`
- `actions`
- `observations`
- `retrieved_laws`
- `law_filter_report`
- `template`
- `extracted_facts`
- `contrastive_example`
- `contrastive_cot`
- `issue_plan`
- `legal_roles`
- `query_strategy`
- `retry_reason`
- `graph_max_steps`
- `generated_document`

### 2.2.3 Agent 工具

当前 Agent 工具固定为：

1. `FactExtractionTool`
2. `RAGSearchTool`
3. `TemplateRetrievalTool`

工具选择方式不是由 LLM 自由决定，而是由状态图节点硬编码绑定。

### 2.2.4 Agent 路由逻辑

当前状态图路由如下：

```text
fact_extraction
  -> rag_search
    -> evidence_filter
      -> template_retrieval
        -> generate
```

同时存在重试回路：

- `rag_search` 没命中 -> 回到 `fact_extraction`
- `evidence_filter` 把结果全裁掉 -> 回到 `fact_extraction`

也就是说，当前 Agent 已具备**有限多轮反思/重试能力**。

### 2.2.5 检索策略升级机制

Agent 的多轮检索不是盲目重复，而是策略升级：

- 第 1 轮：`focused`
- 第 2 轮：`balanced`
- 第 3 轮及以后：`broad`

策略升级后会：

- 扩大 planner query 使用范围
- 增加“相关法律依据/司法解释”后缀 query
- 在必要时引入领域 fallback query

### 2.2.6 证据级筛选

Agent 在拿到候选法条后并不会直接交给 LLM，而是先进入 `evidence_filter`。

筛选时综合考虑：

- 与证据摘要的关键词重叠
- 时间线信息
- 主体结构
- 主体关系
- 主请求
- contrastive focus/trap 命中
- context_tier

输出结果中会记录：

- `evidence_support_score`
- `contrastive_support_score`
- `final_support_score`

### 2.2.7 生成阶段上下文组织

Agent 不是简单把法条平铺进 prompt，而是：

1. 先按父节点聚类法条
2. 组织为“父级路径 + 命中条文 + 相关同簇条文”的小簇
3. 再把这些簇注入生成 prompt

这样做的好处是：

- 减少孤立条文导致的语义断裂
- 保持体系位置
- 控制总上下文长度

### 2.2.8 技术权衡

当前 Agent 的优点：

- 节点清晰、可控、可调试
- 行为可解释
- 支持多轮检索与重试
- 不依赖外部 LangGraph 运行时

当前 Agent 的限制：

- 工具集合固定
- 没有并行 tool execution
- 没有外部搜索与代码执行
- `ask` 问答路径不经过 LegalAgent

### 2.3 RAG 与 Agent 的协作模式

当前协作模式不是“所有回答都走 Agent”，而是分场景：

**问答场景**

- 由 `LegalRAG` 主导
- `QueryAgent` 做检索规划
- `LegalAgent` 不参与

**文书生成场景**

- 由 `LegalAgent` 主导
- `LegalAgent` 在节点中调用 `rag_search`
- RAG 作为 Agent 的工具能力

协作逻辑如下：

1. Agent 先提取事实与争议点
2. 再调用 RAG 检索法条
3. 再根据案件证据对法条做二次筛选
4. 然后将法条簇、模板、事实时间线共同注入 LLM
5. LLM 生成文书正文

这是一种 **“Agent 管流程，RAG 提法律依据”** 的协作模式。

### 2.4 为什么采用这些技术选型

当前技术选型背后的核心考虑是：

1. **优先可控**
   - 法律场景更看重可解释性
   - 因此 Agent 使用显式状态图，而不是黑箱式 ReAct 文本循环

2. **优先本地化部署**
   - 本地 embedding、Milvus-lite、本地 LLM 后端都指向这一目标

3. **优先检索质量，而不是炫技**
   - 当前最花力气的部分其实是 query planning、路径重排、法律优先级重排

4. **优先知识库可维护性**
   - 已经引入增量索引和历史版本过滤
   - 这是法律知识系统比普通 RAG 更关键的一层

## 4. 当前项目结论

从当前完成情况看，本项目已经不是简单的“向量检索 Demo”，而是具备以下特征的本地法律知识系统原型：

1. 有较完整的 RAG 主链路
2. 有可运行的 Agent 文书生成链路
3. 有树状法条结构、路径重排、法律优先级重排
4. 有增量索引和历史版本检索
5. 有任务类型切换的问答模板

但如果从成熟度角度判断，它仍然更接近：

- **中后期研究型原型**
- **面向内部迭代的工程化系统**

而不是完全生产级产品。

最值得继续增强的方向包括：

1. 将稀疏检索正式并入主召回链路
2. 完善多模态解析能力
3. 增强训练型 reranker 或判别式重排模型
4. 提升 Agent 的并行与更细粒度任务调度能力
5. 为历史版本法条提供更直观的展示与引用标识
