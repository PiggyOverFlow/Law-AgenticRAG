# LawRAG 智能法律文书生成系统 - 项目文档

## 一、项目背景

### 1.1 项目概述

LawRAG 是一个基于 RAG（检索增强生成）技术和多模态解析的智能法律文书自动生成系统。该系统通过 Agent 架构结合先进的自然语言处理技术，能够解析用户提供的多元证据材料（文本、图像、音视频），将其结构化为案件事实，并基于本地化的法律法规知识库进行精准检索，最终自动生成符合法定格式要求的法律文书。

### 1.2 核心价值

- **多模态输入支持**：支持文本、图像、音频、视频等多种证据格式的自动解析
- **智能事实提取**：利用 LLM Function Calling 技术将非结构化证据转化为结构化案件事实
- **精准法律检索**：基于向量检索 + 关键词重排 + 元数据过滤的混合检索策略
- **自动化文书生成**：根据案件事实和相关法条自动生成起诉书、答辩状、上诉状等法律文书
- **质量评估体系**：提供专家评审和 LLM 评判双重评估机制

### 1.3 应用场景

- 律师事务所：快速起草法律文书，提高工作效率
- 法律援助：为普通民众提供基础法律文书生成服务
- 司法机关：辅助法官快速梳理案件事实和相关法条
- 法学研究：辅助法律文书教学和研究

## 二、技术栈

### 2.1 核心技术

| 技术类别 | 具体技术 | 用途 |
|---------|---------|------|
| LLM/VLM | Qwen-Max / Qwen-VL | 主要推理模型和视觉语言模型 |
| ASR | Whisper / SenseVoice | 音频语音识别 |
| Embedding | BGE-m3 | 文本向量化嵌入 |
| Reranker | BGE-Reranker-v2-m3 | 检索结果重排序 |
| 向量数据库 | Milvus / Qdrant | 存储和检索法律条文向量 |
| 开发框架 | Python + PyTorch + LangChain | 基础开发框架 |

### 2.2 依赖库

- **数据处理**: Pydantic, pandas, numpy
- **文本处理**: regex, jieba
- **深度学习**: torch, transformers
- **向量数据库**: pymilvus, qdrant-client
- **配置管理**: PyYAML, python-dotenv
- **日志记录**: logging
- **网络请求**: requests

### 3.2 核心模块说明

#### 3.2.1 main.py - 主入口

**作用**: 系统的主入口文件，提供命令行接口（CLI）。

**核心类**: `LawRAG`

**主要功能**:
- 初始化系统各模块（Parser、RAG、Agent、Generator、Evaluator）
- 提供构建索引、解析证据、生成文书、检索法条、评估文书等功能
- 支持多种命令行参数和子命令

**命令行接口**:
```bash
# 构建向量索引
python main.py build [--limit N]

# 生成法律文书
python main.py generate --evidence FILES --type TYPE [--request REQ] [--output FILE]

# 检索法律法规
python main.py search --query QUERY [--top-k K]

# 基于法条证据回答
python main.py ask --query QUERY

# 评估文书质量
python main.py evaluate --document DOC --evidence EVIDENCE --type TYPE [--reference REF]
```

**数据流**: 
1. 解析命令行参数
2. 初始化 LawRAG 实例
3. 根据命令调用相应功能模块
4. 返回结果或保存文件

#### 3.2.2 config.py - 配置管理

**作用**: 统一管理系统配置，支持从 YAML 文件和环境变量加载配置。

**核心类**: `Config`

**配置项**:
- **LLMConfig**: LLM 模型配置（模型名称、API Key、温度等）
- **ASRConfig**: 语音识别配置
- **VectorDBConfig**: 向量数据库配置
- **RAGConfig**: RAG 检索配置（嵌入模型、重排模型、检索参数）
- **DatasetConfig**: 数据集配置
- **MultimodalConfig**: 多模态解析配置
- **AgentConfig**: Agent 配置
- **DocumentConfig**: 文书生成配置
- **EvaluationConfig**: 评估配置
- **LoggingConfig**: 日志配置
- **CacheConfig**: 缓存配置
- **PerformanceConfig**: 性能配置

**数据流**:
1. 从 `bootstrap.yaml` 加载配置
2. 解析环境变量（格式：`${VAR_NAME}`）
3. 转换为对应的配置类实例
4. 提供全局单例访问

#### 3.2.3 src/models/ - 数据模型

**作用**: 定义系统的数据结构和类型约束。

**核心类**:

1. **LegalEvent**: 法律事件
   - `evident_type`: 证据类型（文本/图片/视频/录音）
   - `time`: 事件时间
   - `place`: 事件地点
   - `cause`: 事件起因
   - `process`: 事件经过
   - `result`: 事件结果
   - `source_file`: 来源文件
   - `timestamp`: 时间戳

2. **CaseFacts**: 案件事实
   - `events`: 法律事件列表
   - `evidence_summary`: 证据摘要
   - `key_disputes`: 核心争议点
   - `extracted_at`: 提取时间

3. **TextEvidence/ImageEvidence/AudioEvidence/VideoEvidence**: 各类证据数据结构

**数据流**:
1. Parser 解析原始文件
2. 生成对应的 Evidence 对象
3. 提取 LegalEvent
4. 聚合为 CaseFacts

#### 3.2.4 src/parsers/ - 多模态解析

**作用**: 解析多种格式的证据文件，提取结构化信息。

**核心类**: `MultimodalParser`

**主要方法**:

1. **parse_text(file_path)**: 解析文本文件
   - 支持格式：txt, md, doc, docx, pdf
   - 直接读取文件内容

2. **parse_image(file_path)**: 解析图像文件
   - 支持格式：jpg, jpeg, png, gif, bmp, webp
   - OCR 提取文字
   - 场景描述

3. **parse_audio(file_path)**: 解析音频文件
   - 支持格式：mp3, wav, m4a, flac, aac, ogg
   - 语音转文字（ASR）
   - 时间戳提取

4. **parse_video(file_path)**: 解析视频文件
   - 支持格式：mp4, avi, mov, mkv, flv, wmv
   - 抽帧分析
   - 音频提取

5. **parse_case_facts(file_paths)**: 解析多个文件并生成案件事实
   - 调用对应的解析方法
   - 提取法律事件
   - 生成争议点

**数据流**:
```
原始文件 → 文件类型识别 → 对应解析器 → Evidence 对象 → LegalEvent 提取 → CaseFacts 聚合
```

#### 3.2.5 src/rag/ - RAG 检索

**作用**: 实现法律法规的向量化存储和智能检索。

**核心类**:

1. **LawChunker**: 法律文本切分器
   - 按法律层级切分（编-章-节-条-款-项-目）
   - 生成 LawChunk 对象
   - 保留层级结构信息

2. **MetadataEnricher**: 元数据增强器
   - 为每个 chunk 添加丰富的元数据
   - 包括法律名称、效力级别、生效日期、适用范围等
   - 支持元数据过滤

3. **VectorDBManager**: 向量数据库管理器
   - 使用 Milvus 存储向量
   - 管理集合的创建、插入、查询
   - 支持索引构建和重置

4. **LegalRAG**: 检索器（核心）
   - **QueryAgent**: 查询分析器
     - 判断查询是否需要改写
     - 自动改写查询
     - 提取关键词
   - **EmbeddingModel**: 嵌入模型
     - 支持 Ollama 调用 BGE-m3
     - 支持本地加载 HuggingFace 模型
     - 批量编码优化
   - **Reranker**: 重排器
     - 基于关键词的 IDF 权重
     - 多关键词命中奖励
     - 距离升序排序
   - **Agentic-RAG**: 多轮检索策略
     - 自动生成多个查询变体
     - 去重合并结果
     - 回退到案由级检索

**数据流**:
```
法律文本 → LawChunker 切分 → MetadataEnricher 增强 → EmbeddingModel 编码 → VectorDB 存储
                                                                 ↓
用户查询 → QueryAgent 分析 → EmbeddingModel 编码 → VectorDB 检索 → Reranker 重排 → 返回结果
```

#### 3.2.6 src/agent/ - Agent 推理

**作用**: 基于 ReAct 范式的智能推理，协调各工具完成任务。

**核心类**: `LegalAgent`

**架构**: 基于 StateGraph 的图式推理

**节点（Nodes）**:

1. **fact_extraction**: 事实提取节点
   - 调用 FactExtractionTool
   - 提取案件关键信息
   - 生成时间线

2. **rag_search**: RAG 检索节点
   - 调用 RAGSearchTool
   - 执行 Agentic-RAG 多轮检索
   - 构建多个查询变体
   - 去重合并结果

3. **template_retrieval**: 模板检索节点
   - 调用 TemplateRetrievalTool
   - 获取对应文书类型的模板

4. **generate**: 生成节点
   - 综合所有观察结果
   - 调用 LLM 生成最终文书

**工具（Tools）**:

1. **RAGSearchTool**: 法律法规检索
   - 输入：查询字符串、过滤条件
   - 输出：相关法条列表

2. **TemplateRetrievalTool**: 文书模板检索
   - 输入：文书类型
   - 输出：模板文本

3. **FactExtractionTool**: 事实提取
   - 输入：CaseFacts
   - 输出：关键信息字典

**条件边（Conditional Edges）**:

1. **_route_after_extraction**: 提取完成后路由
   - 有法条 → 模板检索
   - 无法条 → RAG 检索

2. **_route_after_rag**: RAG 检索完成后路由
   - 有模板 → 生成
   - 无模板 → 模板检索

3. **_route_continue**: 判断是否继续迭代
   - 达到最大迭代次数 → 生成
   - 有法条和模板 → 生成
   - 否则 → 继续事实提取

**数据流**:
```
初始状态 → fact_extraction → rag_search → template_retrieval → generate → 最终文书
                ↑_______________↑
```

#### 3.2.7 src/data/ - 数据加载

**作用**: 从数据集加载法律信息并构建索引。

**核心类**:

1. **LawDatasetLoader**: 法律数据集加载器
   - `load_from_sqlite()`: 从 SQLite 数据库加载法律元数据
   - `load_from_folder()`: 直接扫描文件夹中的 Markdown 文件
   - `load_law_content()`: 加载法律条文内容
   - `process_law()`: 处理单部法律，生成 chunks
   - `load_all_laws()`: 加载所有法律

2. **LawIndexBuilder**: 索引构建器
   - `build_full_index()`: 构建完整索引
   - `build_incremental_index()`: 增量索引
   - `rebuild_index()`: 重建索引

**数据流**:
```
SQLite/文件夹 → LawDatasetLoader → 加载法律信息 → 读取法律内容 → LawChunker 切分 → MetadataEnricher 增强 → LegalRAG.build_index() → Milvus 存储
```

#### 3.2.8 src/generation/ - 文书生成

**作用**: 协调 Agent 生成法律文书并保存。

**核心类**:

1. **DocumentGenerator**: 文书生成器
   - `generate_document()`: 生成文书
   - `save_document()`: 保存文书
   - `generate_and_save()`: 生成并保存

2. **DocumentFormatter**: 文书格式化器
   - `format_complaint()`: 格式化起诉书
   - `format_defense()`: 格式化答辩状
   - `_format_party_info()`: 格式化当事人信息

3. **DocumentValidator**: 文书验证器
   - `validate_document()`: 验证文书基本格式
   - `validate_complaint()`: 验证起诉书特定格式

**数据流**:
```
CaseFacts + 文书类型 → DocumentGenerator → Agent.run() → 生成的文书 → DocumentGenerator.save_document() → 保存文件
```

#### 3.2.9 src/evaluation/ - 评估模块

**作用**: 评估生成文书的质量。

**核心类**:

1. **ExpertReviewSystem**: 专家评审系统
   - `create_review_form()`: 创建评审表
   - `submit_review()`: 提交评审
   - `get_review_statistics()`: 获取评审统计
   - `export_reviews()`: 导出评审数据

2. **LLMJudgeAgent**: LLM 评判代理
   - `judge_document()`: 评判文书
   - `_perform_consistency_check()`: 一致性检验
   - `_perform_logic_coherence_check()`: 逻辑连贯性检验
   - `_calculate_overall_score()`: 计算总分
   - `_generate_detailed_feedback()`: 生成详细反馈

3. **EvaluationFramework**: 评估框架
   - `evaluate_document()`: 评估文书
   - `generate_evaluation_report()`: 生成评估报告

**评估维度**:
- 格式正确性（0-5分）
- 内容完整性（0-5分）
- 逻辑条理性（0-5分）
- 内容准确性（0-5分）
- 法条适用性（0-5分）

**数据流**:
```
生成的文书 + 原始证据 → EvaluationFramework → ExpertReviewSystem / LLMJudgeAgent → 评估结果
```

#### 3.2.10 src/finetuning/ - 微调模块

**核心文件**:
- **LoraQwenModel.py**: LoRA 微调 Qwen 模型
- **download.py**: 模型下载脚本

## 七、架构设计亮点

### 7.1 模块化设计

- **高内聚低耦合**: 每个模块职责单一，接口清晰
- **易于扩展**: 新增文书类型、解析器、工具都很方便
- **可测试性**: 每个模块都可以独立测试

### 7.2 智能检索策略

- **Agentic-RAG**: 多轮检索，自动改写查询
- **混合检索**: 向量检索 + 关键词重排 + 元数据过滤
- **回退机制**: 语义检索失败时回退到案由级检索

### 7.3 多模态支持

- **统一接口**: 不同格式的证据文件通过统一接口解析
- **结构化输出**: 使用 Pydantic 强类型约束
- **时间戳保留**: 音视频证据保留时间戳，便于定位

### 7.4 Agent 推理

- **StateGraph**: 基于图的推理，清晰的状态流转
- **工具调用**: 模块化的工具设计，易于扩展
- **条件路由**: 智能决策下一步操作

### 7.5 质量保证

- **双重评估**: 专家评审 + LLM 评判
- **多维度**: 格式、完整性、逻辑、准确性、法条适用性
- **详细反馈**: 提供具体的改进建议

## 八、性能优化

### 8.1 缓存机制

- **Redis 缓存**: 缓存 LLM 调用结果

## 九、常见问题

### 9.1 向量数据库连接失败

**问题**: Milvus 连接失败

**解决方案**:
1. 检查 Milvus 服务是否启动
2. 检查配置中的 host 和 port 是否正确
3. 检查防火墙设置

### 9.2 LLM 调用失败

**问题**: LLM API 调用失败

**解决方案**:
1. 确认 API Key 已正确设置
2. 检查网络连接
3. 检查 API 配额
4. 查看日志中的详细错误信息

### 9.3 索引构建很慢

**问题**: 索引构建速度慢

**解决方案**:
1. 使用 `--limit` 参数限制处理数量
2. 使用 GPU 加速嵌入计算
3. 调整 `chunk_size` 和 `chunk_overlap` 参数
4. 使用 Ollama 本地模型而非远程 API

### 9.4 生成的文书质量不理想

**问题**: 文书质量不理想

**解决方案**:
1. 检查证据材料是否完整清晰
2. 调整 LLM 的 temperature 参数
3. 使用评估系统分析问题所在
4. 检查检索到的法条是否相关
5. 调整检索参数（top_k_initial, top_k_final）

### 9.5 Ollama 模型加载失败

**问题**: Ollama 模型加载失败

**解决方案**:
1. 确认 Ollama 服务已启动
2. 确认模型已下载（`ollama pull bge-m3`）
3. 检查配置中的 base_url 是否正确
4. 查看日志中的详细错误信息
